# pagerly_escalation_policy (Resource)

Who is paged, in up to three layers, and how long to wait between them.

## Example Usage

```hcl
resource "pagerly_escalation_policy" "payments_p1" {
  name = "Payments P1"
  layer = [
    { team_id = pagerly_team.payments.id, wait_minutes = 5 },
    { people = ["cto@example.com"], wait_minutes = 10 },
    { team_id = pagerly_team.platform.id },
  ]
  repeat        = 1
  slack_channel = "C0123456789"
}
```

A policy that an alert integration still sends alerts to cannot be deleted; point the
integration elsewhere first.

## Schema

### Required

- `layer` (Attributes List) Layers in the order they are paged. A layer needs a team, people, or both. (see [below for nested schema](#nestedatt--layer))
- `name` (String) Policy name.

### Optional

- `repeat` (Number) Times to start again from layer 1 when nobody acknowledges (0–9).
- `slack_channel` (String) Slack channel id where incidents routed to this policy by an alert integration are posted.

### Read-Only

- `id` (String) The ID of this resource.

<a id="nestedatt--layer"></a>
### Nested Schema for `layer`

Optional:

- `people` (List of String) Emails of people to page directly. They must be in the Pagerly user directory.
- `team_id` (String) Page whoever is on call for this team.
- `wait_minutes` (Number) Minutes to wait for an acknowledgement before the next layer. Layer 1 defaults to 5.
